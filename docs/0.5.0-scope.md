# vibe-scenarios.yaml — scope for 0.5.0

**Status:** Scoped, not yet implemented. Targets release 0.5.0.

**One-line goal:** Let the AI author a test plan as YAML; vibe-test executes it in Playwright. Heuristic CRUD generation becomes optional fallback.

## Why this is the right next move

AI assistants already read code and write text well. What they need from vibe-test is a *data plane* for handing test plans to a browser. Heuristic regex CRUD can't express absence assertions or state-machine UI; authored YAML can.

Division of labor:
- **AI is the brain.** Reads code + `VIBE.md` + spec docs, drafts scenarios that are specific to *this* project.
- **vibe-test is the eyes.** Executes those scenarios in a real browser, screenshots, asserts, reports.

Current heuristic engine generates ~5–15 scenarios per route of dubious value (random `vt...@gmail.com` creds, generic "Submit empty form" tests, hardcoded "Active" filter clicks). Authored YAML produces N scenarios of real value, scaling with how much context the AI has about the project.

## Schema (v1)

```yaml
version: 1

# Optional. Lets individual scenarios opt into a specific account.
# Without roles{}, all scenarios use config.auth.credentials.
roles:
  student: { email: student1.dev@example.com, password: ... }
  teacher: { email: teacher.dev@example.com, password: ... }

scenarios:
  - id: T2-cutoff
    name: Mode A cutoff passed → doors closed
    role: student              # optional, defaults to config.auth.credentials
    priority: high              # high | medium | low (drives report ordering)
    tags: [live-v2, privacy]    # optional, for grouping
    skip_reason: null           # optional — marks skipped without deleting

    steps:
      - navigate: /live/dev-cutoff-passed
      - wait_for: { text: /doors closed/i, timeout_ms: 5000 }
      - screenshot: cutoff-state

    assert:
      present:                  # all must be visible
        - { text: /doors closed/i }
        - { role: link, name: /back to today/i }
      absent:                   # the killer feature — none may be visible
        - { text: /green room/i }
        - { test_id: preroom-camera-checkbox }
      url_matches: /\/live\/dev-cutoff-passed$/
      no_api_errors: true
```

### Step actions (v1)

| Action | Shape |
|---|---|
| `navigate` | `<path>` string |
| `click` | selector spec |
| `fill` | `{ target: <selector>, value: string }` |
| `wait_for` | selector spec OR `{ text, timeout_ms }` OR `{ url, timeout_ms }` OR `{ ms }` |
| `screenshot` | `<name>` string → `.vibe/screenshots/<scenario-id>-<name>.png` |
| `eval` | `<js expression>` — for invariant probes (e.g. `localStorage.getItem('token')`); result captured in report |
| `assert` | inline assertion block — same shape as scenario-level `assert`, can run mid-flow |

### Selector spec

Any combination of:

```yaml
text: "Sign out"            # string or /regex/i
role: button                # WAI-ARIA role
name: "Submit"              # accessible name (used with role)
test_id: "preroom-camera"   # data-testid attribute
css: "button.primary"       # raw CSS, last resort
label: "Email"              # form label
placeholder: "you@example"  # input placeholder
checked: true               # additional constraint
visible: true               # default true
```

### Assertion shapes

- `present: [<selector spec>...]` — each must be visible
- `absent: [<selector spec>...]` — **none may be visible** (the killer feature for privacy invariants)
- `url_matches: /regex/`
- `text_matches: /regex/` — body text contains
- `api_status: { url: <substring>, status: <int> }` — at least one observed network call matches
- `no_api_errors: true` — no 4xx/5xx observed during scenario

## IN for 0.5.0

- YAML schema + loader + zod validator
- Compiler to internal `TestScenario` shape (no rewrite of execution path)
- `present` / `absent` / `url_matches` / `text_matches` / `api_status` / `no_api_errors` assertions
- Per-scenario `role:` (single-browser, batched by role to minimize re-auth)
- `vibe-test validate <file>` CLI subcommand with line-precise errors
- Heuristic generator becomes opt-in; authored YAML wins when present
- Tests for parser, compiler, runner

## OUT for 0.5.0 (explicitly, defer to 0.6.0+)

- **True multi-actor coordination** (teacher + student in the *same* scenario watching each other) — needs a second browser context with a shared event bus. Stretch goal for 0.6.0.
- **LLM-driven scenario generation** (e.g. `suggest_scenarios(feature)` MCP tool calling Anthropic API to draft YAML from code + `VIBE.md`) — needs API key plumbing and a cost model. 0.6.0.
- **Scenario inheritance** (`extends: another-scenario-id`) — wait for real usage to drive the syntax.
- **Visual regression baselining** — orthogonal feature, separate release.

## Effort estimate

- ~3–4 focused days

- Backwards compatible: projects without `vibe-scenarios.yaml` still get heuristic generation unchanged

## Risks + mitigations

1. **Selector-spec API is hard to change later.**
   Mitigation: ship zod-validated with explicit `version: 1` field. Reserve `version: 2` for breaking changes. Document the shape clearly in `VIBE.example.md`.

2. **Role switching slow if re-auth per scenario.**
   Mitigation: group scenarios by role; reuse `storageState` within a role. Single browser, but smart ordering.

3. **AI produces malformed YAML.**
   Mitigation: `vibe-test validate` with line-precise zod errors. Ship `VIBE.example.md` with a complete working file the AI can use as a template.

4. **Two scenario systems to maintain (heuristic + authored).**
   Mitigation: `scenarios: "authored"` mode deprecates heuristic for projects that opt in. Heuristic stays for greenfield projects with no YAML yet. After a quarter of real usage, consider deprecating heuristic entirely if usage is low.

## Success criteria (concrete)

- The 7 single-browser Live Classes v2 scenarios that motivated this release (T1, T2, T3, T5, T9, T12, T13 from the DhyanHQ testing brief) are expressible in `vibe-scenarios.yaml` without hacks.
- A run produces results indistinguishable from hand-written Playwright — no false-positive "error visible on page" verdicts on legitimate UI states like "doors closed" or "session ended".
- An AI assistant can author the file in one shot after reading the codebase + spec docs, without back-and-forth on YAML syntax.
- Projects with both authored and heuristic enabled see authored scenarios run first; heuristic only fills gaps.

## Implementation order (for the dev picking this up)

1. **Schema + loader + validator** — write the zod schemas first, then the YAML loader. Add `vibe-test validate <file>` CLI subcommand. Land this alone as a PR; no behavior change yet.
2. **Compiler** — `AuthoredScenario → TestScenario`. Existing tests should pass unchanged.
3. **New step actions** (`wait_for`, `screenshot`, `eval`) + **new assertions** (`present`, `absent`, `url_matches`, `text_matches`, `api_status`, `no_api_errors`) in `runner.ts` and `verifier.ts`.
4. **Role batching** in `runner.ts`.
5. **Mode switch** in `engine/index.ts` (`"authored" | "heuristic" | "both"`).
6. **Docs** — `README.md`, `CHANGELOG.md`, `llms.txt`, `VIBE.example.md`.
7. **Release** — `npm version minor` → `0.5.0`, push, tag.

Each step should be a separate commit. Tests pass at every step.
